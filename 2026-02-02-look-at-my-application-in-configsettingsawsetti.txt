  3. Use Hyprland's hyprctl for positioning — Set PySide6 windows as

  and position them. Less precise but no native code needed.

  I'd recommend option 1 if pyside6-layer-shell is mature enough for your needs

● Component Architecture — Section 1: Layer Shell Foundation

  Every visible shell element (bar, dock, notch) needs to be a Wayland
  layer-shell surface. In PySide6, this means each top-level component is a
  QWindow/QWidget configured through pyside6-layer-shell rather than a normal
  desktop window.

  I'd propose a base class hierarchy:

  ShellSurface (QWidget + layer-shell config)
  ├── PanelSurface    → anchored to edge, reserves space (bar)
  ├── OverlaySurface  → floats above, no space reservation (notch, launcher,
  dashboard)
  └── DockSurface     → auto-hide edge surface (dock)

  ShellSurface would encapsulate:
  - Layer-shell setup (layer, anchors, margins, exclusive zone)
  - Per-monitor instantiation (your current MonitorManager pattern — each
  monitor gets its own bar/dock/notch)
  - The Animator integration — every surface gets slide_in() / slide_out()
  methods that animate based on its anchor edge
  - Occlusion awareness — surfaces check fullscreen window state and auto-hide

  PanelSurface (bar) sets an exclusive zone so windows don't overlap it.
  Anchored to all 4 edges of one side (e.g., top-left + top-right = full-width
  top bar).

  OverlaySurface (notch/dashboard/launcher) lives on the overlay layer, no
  exclusive zone, keyboard interactivity on demand. This is what appears on
  SUPER+D — it grabs keyboard focus when revealed.

  DockSurface extends OverlaySurface with hover detection — a thin invisible
  input region that triggers reveal, matching your current
  _on_hover_enter/_on_hover_leave + 250ms delay pattern.

  Does this surface hierarchy make sense for your use case, or should I adjust
  the split?

● Component Architecture — Section 2: The Animator

  A single reusable class that replaces both utils/animator.py and the Fabric
  Revealer concept. Every shell component uses it the same way.

  class Animator:
      # Default curve matching your current spring overshoot
      SPRING = QEasingCurve(QEasingCurve.BezierSpline)
      # control points: (0.175, 0.885, 0.32, 1.275)

      @staticmethod
      def slide(widget, direction, duration=250, curve=SPRING) -> 
  QPropertyAnimation
      
      @staticmethod
      def fade(widget, start, end, duration=250, curve=SPRING) -> 
  QPropertyAnimation
      
      @staticmethod
      def group(*animations, parallel=True) -> QAnimationGroup

  The key insight from your codebase: almost every animation is a slide + 
  optional fade with the same curve and duration. So instead of each component
  reimplementing animation logic, they call:

  # Notch opening
  Animator.group(
      Animator.slide(self, "down", duration=250),
      Animator.fade(self, 0.0, 1.0, duration=250),
  )

  How slide direction is determined: Each ShellSurface knows its anchor edge.
  slide("in") and slide("out") resolve to the correct axis automatically — a
  top-anchored notch slides down to reveal, a bottom-anchored dock slides up. No
   per-component direction logic needed.

  Special cases from your current code:
  - Launcher slot stagger: Animator.fade(slot, 0, 1, duration=500, curve=EASE)
  called per-slot with increasing delays
  - Compact stack: 100ms duration override
  - Dock hover delay: not an animation — just a QTimer.singleShot(250, 
  self._maybe_hide)

  Does this animator API feel right, or do you want it structured differently?

● Component Architecture — Section 4: Theming Layer

  You already have Glaze handling this for PySide6. The current architecture is
  solid — a Theme dataclass with 70+ properties, Material You generation via
  Matugen from wallpapers, and stylesheet generation. The settings dialog
  already uses it.

  The gap is that your Fabric/GTK3 components use CSS variables (var(--surface),
   var(--accent)) in .css files, while Glaze generates Qt stylesheets with
  inline color values. For the full PySide6 shell, I'd extend Glaze with:

  1. Live theme reload: When the wallpaper changes and Matugen regenerates
  colors, every ShellSurface calls refresh_theme(). Your FramelessMainWindow
  already has this method — it just needs to propagate to all shell surfaces.

  2. Component-level stylesheet fragments: Instead of one massive stylesheet,
  each component registers its style rules with Glaze. On theme change, Glaze
  regenerates and reapplies only what changed.

  # In any component
  class DashboardView(QWidget):
      def get_stylesheet(self, t: Theme) -> str:
          return f"""
              #dashboard-card {{
                  background: {t.surface};
                  border-radius: {t.corner_radius}px;
              }}
          """

  This mirrors how your get_extra_stylesheet() works in aw_settings.py — each
  component owns its styles, Glaze just provides the theme values.

  3. Animated theme transitions: When colors change (wallpaper swap), instead of
   an instant repaint, Animator.fade the entire surface's opacity briefly (150ms
   out, apply theme, 150ms in). Subtle but avoids the jarring flash your GTK
  version has.

  What stays the same: Glaze's Theme.from_material_palette(), the
  get_current_theme() / set_current_theme() API, and all the widget classes
  (ThemedComboBox, DonateButton, etc.) carry over unchanged.

  Does this theming approach work, or do you want something different for live
  color transitions?

● Component Architecture — Section 5: Services & State Management

  Currently your state flows through several patterns: Fabric's built-in service
   system, GObject signals, config.data bind vars, and direct instance
  references (e.g., Dock._instances, Notch._instance). For PySide6, this
  consolidates cleanly into Qt's native signal/slot system.

  Central state bus:

  class ShellState(QObject):
      # Signals any component can connect to
      bar_toggled = Signal(bool)          # visible/hidden
      notch_opened = Signal(str)          # module name
      notch_closed = Signal()
      theme_changed = Signal(Theme)
      workspace_changed = Signal(int)
      monitor_focused = Signal(str)       # monitor name
      occlusion_changed = Signal(str, bool)  # surface_id, occluded

      # Replaces config.data bind_vars for runtime state
      config: dict  # loaded from settings_utils

  Every ShellSurface receives a reference to ShellState at construction. Instead
   of Dock._instances class-level tracking, the state bus coordinates:

  # Keybind handler (replaces global_keybinds.py)
  def on_super_d(self):
      self.state.notch_opened.emit("dashboard")

  # In NotchSurface.__init__
  self.state.notch_opened.connect(self._on_open)
  self.state.bar_toggled.connect(self._on_bar_toggle)

  Services map directly:
  Current Service: services/brightness.py
  PySide6 Equivalent: QObject with D-Bus calls via QtDBus

  Current Service: services/mpris.py
  PySide6 Equivalent: QObject with D-Bus MPRIS interface
  ────────────────────────────────────────
  Current Service: services/network.py
  PySide6 Equivalent: QObject wrapping NetworkManager D-Bus
  ────────────────────────────────────────
  Current Service: services/monitor_focus.py

  Current Service: utils/occlusion.py

● Component Architecture — Section 7: Migration Strategy

  The key constraint: the shell must stay functional throughout. You can't rip
  out Fabric and have nothing for a week. Here's the order, each step producing
  a working shell:

  Phase 1 — Foundation (no visible change)
  Build core/ — surface.py, animator.py, state.py, hyprland.py, occlusion.py.
  These have zero dependencies on Fabric. You can write and test them in
  isolation. The Animator can be validated with a throwaway test window.
  HyprlandListener can be tested by just printing events.

  Phase 2 — Bar
  First visible component. The bar is the simplest surface — it's a PanelSurface
   with a horizontal layout of widgets. Port modules/bar.py to surfaces/bar.py.
  At this point main.py has a flag:

  USE_PYSIDE = {"bar": True, "notch": False, "dock": False}

  Fabric still runs the notch and dock. PySide6 runs the bar. They coexist —
  both connect to Hyprland IPC independently, both read the same config. The
  layer-shell compositor doesn't care that they're different toolkits.

  Phase 3 — Dock
  Port modules/dock.py to surfaces/dock.py. Hover reveal, app buttons,
  occlusion. Flip the flag.

  Phase 4 — Notch (shell)
  Port the notch surface + compact view only. No inner views yet — just the
  resting state (clock, media info). The notch slides open but shows a
  placeholder.

  Phase 5 — Views (iterative)
  Port views one at a time into the notch's AnimatedStack. Each one is
  independent:
  1. Dashboard (most used)
  2. Launcher (most complex — async app loading, search)
  3. Power menu (simple)
  4. Then the rest in any order

  Phase 6 — Remove Fabric
  Once all flags are True, delete the Fabric dependency, modules/, old CSS
  files, and the feature flags.

  Each phase is a meaningful commit on devsh that you can test and live with
  before moving on. Does this incremental plan work, or would you prefer a
  different ordering?
